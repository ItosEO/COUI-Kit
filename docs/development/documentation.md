# 如何维护文档

修改 Slider 的步进语义时，更新 Slider 页面；修改融合输入坐标时，更新融合效果页面。让读者能按新行为接入，是同一个 PR 的交付内容。

## 文件归属

| 内容                         | 唯一维护位置           |
|----------------------------|------------------|
| 项目能力和使用导航                  | 根 README         |
| AI 开发任务阅读入口与执行权限           | AGENTS.md        |
| 源码接入、兼容要求、外观和 Demo 操作      | docs/guide       |
| 可直接放入布局的控件及受控状态            | docs/components  |
| 可独立调用的绘制、采样、光效和算法          | docs/effects     |
| 开发流程、架构、代码与 API 规范、复刻和评审方法 | docs/development |
| 具体决定的依据、备选和历史证据            | 对应 Note          |
| 完整参数声明、默认值和固定算法常量          | 源码、KDoc 和构建配置    |

顶栏是 component，顶栏使用的渐进模糊是 effect；组件页讲装配与回调，效果页讲采样、坐标和绘制契约。共用要求在所属页完整维护，其他页面链接过去。

## 哪些改动必须更新文档

| 改动                    | 同步内容                                             |
|-----------------------|--------------------------------------------------|
| 新增 component 或 effect | 新建对应页面，加入本目录 README，提供公开 API 示例与源码入口；按任务范围补 Demo |
| 重命名或移除公开入口            | 更新页面、目录、示例和入站链接；迁移方式写入 PR，发行时记入 CHANGELOG |
| 参数、回调、受控状态或生命周期语义变化   | 更新对应页面的用法、责任划分和相关示例                              |
| 平台门槛、依赖要求或失败行为变化      | 更新兼容要求与受影响页面，保留明确的平台分支                           |
| 采样、单位、坐标或合成要求变化       | 更新对应 effect 和使用它的 component 装配说明                 |
| 纯内部实现调整，使用契约不变        | 按需更新开发文档、KDoc 和 Note；PR 说明普通使用文档无需修改的原因          |
| 仅调整实现参数，使用契约不变        | 在代码维护参数；不复制一套数值到文档                               |

## Component 页面

文件名用英文小写和连字符，与目录链接保持一致。标题使用组件名称，开头用一句话说明它帮助用户做什么。

按实际需要组织以下内容，不建立空章节：

1. 用途与可见结果。已有真实图片或视频时可以引用，不用占位图冒充效果。
2. 基本用法。给出一项完整且有用的操作，说明示例运行位置及传入的宿主依赖。
3. 状态与事件。说明谁持有值、如何更新、回调何时提交，以及禁用或重复点击的行为。
4. 外观与预设。引用所属 Defaults；参数解释聚焦语义，不抄常量和全部默认值。
5. 平台与装配。列出该组件的版本门槛、父容器、采样源、inset、语义及失败处理要求。
6. 完整示例与 API。链接到公开声明和 Demo 的具体文件，内部辅助类不作为接入入口。

可参考[滑条](../components/slider.md)、[复选框](../components/checkbox.md)和[菜单](../components/menu.md)。组件名、符号和示例必须对应当前公开 API。

## Effect 页面

先给使用者能观察到的结果，再介绍一条可实际调用的绘制链：

1. 最小用法与公开入口，区分便捷入口和底层自定义。
2. 输入、单位与坐标系；说明本地、窗口、屏幕坐标的转换责任。
3. 采样与合成；是否需要背景源、源与消费者怎样分层，以及蒙版或 alpha 的含义。
4. 资源与生命周期；谁持有可变 renderer，主题、尺寸或状态变化时由谁更新。
5. 平台门槛、错误与已有替代路径；不要把不同算法写成等价。
6. 完整装配和源码链接。原厂研究过程放在复刻指南或 Note。

可参考[阴影](../effects/shadow.md)和[融合](../effects/metaball.md)。像素算法没有业务事件时，不强加组件式的点击或状态章节。

## 示例与措辞

- Kotlin 示例使用公开 API，给出必要 import。完整函数的 Modifier 放在首位并提供默认值；片段须说明所在的 Compose 或绘制作用域。
- 宿主参数必须注明来源，不能调用 Demo 私有函数或要求依赖 Demo。应用文案作为函数参数传入，实际 App 放入字符串资源。
- 示例尺寸、颜色和输入用于演示一项技术，不称为官方默认。固定预设直接引用 Defaults。
- 必须知道的限制写在对应操作附近。只有高级自定义才需要的坐标与合成细节，放到效果页。
- 使用者完成接入所需的信息要在普通文档内完整；Note 用于追溯理由，不代替使用步骤。
- 使用文档面向首次接入者，直接说明当前用法。删除“已改为”“仍保留旧调用”等变更叙述，以及重复的正确性保证；具体版本变化与迁移步骤归 CHANGELOG，决定依据归 Note，单轮检查与交付过程归 PR。

## 提交前

核对示例的 import、公开可见性、必填参数和回调，检查目录可达、相对链接与章节锚点，执行 git diff --check。改动代码时同时检查对应文档示例；移动页面时更新所有入站链接。

在 PR 的“使用文档”中列出修改路径和用法影响。未更新普通文档时，说明为什么使用契约没有变化。文档检查不能写成 Android 构建或设备验收通过。
